# Нагрузочное тестирование ручек диалогов

Тестируются все три ручки контроллера [`internal/api/dialog.go`](../../internal/api/dialog.go):

| Ручка | Метод | Handler |
|---|---|---|
| `/api/v1/dialog/list` | GET | `GetDialogList` |
| `/api/v1/dialog/{user_id}/list` | GET | `GetDialogMessages` |
| `/api/v1/dialog/{user_id}/send` | POST | `PostDialogUserIdSend` |

Все три ручки требуют авторизации (`security: [{bearerAuth: []}]`), поэтому каждый
запрос отправляется с заголовком `Authorization: Bearer <JWT>`.

## Условия проведения

| Параметр | Значение |
|---|---|
| Дата | 2026-08-03 |
| Хост | Apple M5 Pro, 18 ядер, macOS 26.5.2 |
| Docker | 29.3.1 |
| Стенд | `deployments/docker-compose-replicated.yaml` — Postgres 18 (1 мастер + 2 реплики) + NATS 2.10 |
| Приложение | контейнер `sm-app`, `localhost:8282` |
| Утилита | `hey` 0.1.5 (`/opt/homebrew/bin/hey`) |
| Длительность прогона | 30 секунд (`-z 30s`) |
| Таймаут запроса | 20 секунд (значение `hey` по умолчанию) |
| Уровни нагрузки | `-c 1`, `-c 10`, `-c 100`, `-c 1000` |
| Лимит дескрипторов | `ulimit -n` = 1048576 |

Хранилище — **Postgres**, реализация в `internal/repository/dialog.go`. Отдельной
in-memory реализации в дереве исходников на момент замера нет, поэтому приведённые
цифры являются базовой линией для Postgres.

### Подготовка данных

Зарегистрированы два пользователя:

* отправитель — `cd399938-2380-4a24-973c-c2f704ca6d23`
* получатель — `092d4acd-81d9-444b-b4c1-79e927591060`

Перед замерами в диалог засеяно **2000 сообщений** (`hey -n 2000 -c 50`, все ответы `201`),
чтобы читающие ручки работали по реальному объёму данных, а не по одной строке.

Порядок прогонов: сначала обе читающие ручки, затем пишущая. Благодаря этому
read-тесты выполнялись на стабильном наборе из ~2001 сообщения и не искажались
ростом таблицы от write-теста. После всех прогонов в `dialog_message` — 735 474 строки.

### Как воспроизвести

```bash
TOKEN=<jwt> DST=<user_id> ./docs/task7/run-load-tests.sh
```

Скрипт: [`run-load-tests.sh`](run-load-tests.sh). Сырой вывод каждого прогона —
в папке [`raw/`](raw/), имена файлов вида `<route>_c<N>.log`; точная команда
записана в заголовке каждого файла.

Ни в одном из 12 прогонов не было ошибок — раздел `Error distribution` пуст во всех
файлах, коды ответов только `200` / `201`.

> ⚠️ **Оговорка к прогону `/dialog/list` при c=1000.** В `hey` 0.1.5 число сохраняемых
> замеров ограничено 1 000 000; счётчик для `Requests/sec` при этом продолжает считать
> все запросы. Этот прогон — единственный из 12, который упёрся в лимит: в гистограмме
> и в распределении кодов ровно 1 000 000 ответов, тогда как `Requests/sec` × `Total`
> даёт ≈1 267 343 фактических запроса. Проверка: в остальных 11 файлах
> `Requests/sec` × `Total` совпадает с числом ответов с точностью до единицы.
>
> Практический вывод: **throughput 42 201 req/s — настоящий**, а латентность 30.0ms
> (и перцентили) посчитаны по первым 1 000 000 запросам, то есть примерно по 79%
> выборки. Реальная средняя латентность на этом прогоне может быть немного выше.

## Выводы

1. **Пропускная способность растёт с ростом конкурентности до определённого предела.**
   У `/dialog/list` — монотонный рост вплоть до c=1000 (2.8k → 42.2k req/s): ручка
   возвращает список из одного диалога, ответ 130 байт, узкого места по данным нет.

2. **Читающая ручка сообщений упирается в потолок между c=100 и c=1000.** Throughput
   `/dialog/{id}/list` практически не меняется (6392 → 6383 req/s), а средняя латентность
   растёт в 9 раз (15.6ms → 141.1ms), p99 — с 41ms до 859ms, худший запрос — 7.4 секунды.
   Это классическое насыщение: система уже отдаёт максимум, и дополнительные клиенты
   лишь встают в очередь. Здесь же единственный прогон, где `hey` не уложился в
   30 секунд (33.4s) — потребовалось время на слив очереди.

3. **Пишущая ручка ведёт себя так же.** `/dialog/{id}/send` растёт до c=100
   (9239 req/s), а при c=1000 даже слегка проседает (8857 req/s) при десятикратном
   росте латентности. Точка насыщения записи — около 100 одновременных клиентов.

4. **Запись оказалась быстрее чтения страницы сообщений** на всех уровнях нагрузки
   (например, при c=100: 10.8ms против 15.6ms). Вставка одной строки дешевле, чем
   выборка страницы из 100 сообщений с сортировкой.

5. **Деградации в ошибки нет.** Даже при 1000 одновременных клиентов сервис не отдал
   ни одной ошибки и не отвалился по таймауту — нагрузка выражается в росте латентности,
   а не в отказах.
