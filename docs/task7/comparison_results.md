# Сравнение результатов нагрузочного тестирования: до/после кэширования

Сравниваются два прогона нагрузочного тестирования ручек диалогов
([`internal/api/dialog.go`](../../internal/api/dialog.go)) утилитой `hey`, выполненные
по одному и тому же скрипту [`run-load-tests.sh`](run-load-tests.sh):

* **before** — [`raw_before/`](raw_before/), ветка до изменений, хранилище — только
  Postgres (мастер + 2 реплики), кэша нет. Описание — [`task-7-load-tests.md`](task-7-load-tests.md).
* **after** — [`raw_after/`](raw_after/), ветка `task-7-inmem-db`: добавлено кэширование
  `resolveDialogID` и страницы последних сообщений диалога в Redis Cluster
  (`internal/service/dialog.go`), стенд — `deployments/docker-compose-in-memory-db.yaml`
  (3 мастера Postgres + Redis Cluster из 3 нод + NATS).

## Условия проведения (after)

| Параметр | Значение |
|---|---|
| Дата | 2026-10-17 |
| Хост | тот же, что в `before`: Apple M5 Pro, 18 ядер, macOS 26.6.2 |
| Docker | 29.3.1 |
| Стенд | `deployments/docker-compose-in-memory-db.yaml` — Postgres 18 (1 мастер + 2 реплики) + Redis Cluster (3 мастер-ноды) + NATS 2.10 |
| Приложение | контейнер `sm-app`, `localhost:8282`, `CACHE_DRIVER=redis` |
| Утилита | `hey` (`/opt/homebrew/bin/hey`) |
| Длительность прогона | 30 секунд (`-z 30s`) |
| Уровни нагрузки | `-c 1`, `-c 10`, `-c 100`, `-c 1000` |
| Порядок прогонов | как в `before`: сначала обе читающие ручки, затем пишущая |
| Подготовка данных | новая пара пользователей, в диалог засеяно 2000 сообщений (`hey -n 2000 -c 50`, все `201`) — тот же объём, что и в `before` |

Сырой вывод — в папке [`raw_after/`](raw_after/), имена файлов те же, что в `raw_before/`.
Ни в одном из 12 прогонов ошибок нет (коды ответов только `200`/`201`, раздел
`Error distribution` пуст во всех файлах).

**Важная оговорка по сопоставимости.** В `after`-стенде одновременно с приложением и
Postgres крутится ещё и 3-нодовый Redis Cluster (плюс одноразовый `sm-redis-cluster-init`),
которого не было в `before`. Это дополнительная фоновая нагрузка на тот же хост с теми же
18 ядрами, и часть замеченной просадки на некэшируемых ручках (`dialog_list`, запись в
`dialog_send`) правдоподобно объясняется именно конкуренцией за CPU между контейнерами,
а не регрессией в коде. Разделить эти два эффекта в рамках одного прогона на одной машине
нельзя — для точного вывода нужен повтор с изолированным Redis на отдельном хосте.

## Результаты по ручкам

### `GET /dialog/list` (кэш не используется этой ручкой)

| N clients | Avg before → after | req/s before → after | Δ req/s |
|-----|----------------|---------------|---|
| 1 | 0.4ms → 0.5ms | 2777.21 → 1835.67 | **-33.9%** |
| 10 | 1.1ms → 1.3ms | 9176.90 → 7535.49 | **-17.9%** |
| 100 | 4.0ms → 5.6ms | 24741.23 → 17729.52 | **-28.3%** |
| 1000 | 30.0ms → 41.1ms | 42201.03 → 24335.06 | **-42.3%** |

Ручка не обращается к `resolveDialogID`/кэшу страниц — кэширование её не касается.
Просадка на всех уровнях конкурентности — признак фоновой нагрузки от Redis Cluster
на том же хосте, а не последствие изменений в коде этой ручки.

### `GET /dialog/{user_id}/list` (использует кэш `resolveDialogID` + кэш страницы)

| N clients | Avg before → after | req/s before → after | Δ req/s |
|-----|----------------|---------------|---|
| 1 | 0.8ms → 1.0ms | 1305.32 → 1044.87 | -19.9% |
| 10 | 2.4ms → 2.5ms | 4251.91 → 4041.56 | -4.9% |
| 100 | 15.6ms → 14.8ms | 6392.00 → 6769.55 | **+5.9%** |
| 1000 | 141.1ms → 133.1ms | 6383.43 → 7502.97 | **+17.5%** |

Это единственная ручка, где эффект кэширования виден напрямую: при c=100 и c=1000 —
именно там, где `before` упирался в насыщение Postgres — throughput вырос, а средняя
латентность снизилась. Хвост задержки тоже заметно короче: p99 на c=1000 упал с 858.7ms
до 269.6ms, хотя единичный худший запрос стал медленнее (9.03s против 7.44s в `before` —
вероятно, холодный промах кэша под пиковой конкурентностью). При c=1 и c=10 кэш не успевает
окупить накладные расходы на поход в Redis при и так малой конкурентности — здесь видна та
же просадка, что и у `dialog_list`.

### `POST /dialog/{user_id}/send` (обновляет кэш `resolveDialogID` и дописывает кэш страницы)

| N clients | Avg before → after | req/s before → after | Δ req/s |
|-----|----------------|---------------|---|
| 1 | 0.7ms → 1.0ms | 1342.59 → 1032.88 | -23.1% |
| 10 | 2.0ms → 2.5ms | 4975.58 → 3933.56 | -20.9% |
| 100 | 10.8ms → 11.7ms | 9238.58 → 8562.33 | -7.3% |
| 1000 | 112.7ms → 119.1ms | 8857.10 → 8378.58 | -5.4% |

Запись теперь дополнительно пишет в Redis (`Set` для `resolveDialogID` и `AppendIfWarm`
для страницы), поэтому каждый запрос стал немного дороже — просадка `req/s` на всех
уровнях конкурентности это отражает. Деградация меньше, чем у `dialog_list` (которая
вообще не трогает кэш), что говорит в пользу гипотезы о фоновой нагрузке как основном
факторе, а не о том, что запись в кэш сама по себе дорогая.

## Выводы

1. **Кэширование `resolveDialogID` и страницы сообщений оправдывает себя именно там, где
   это было нужно** — на `GET /dialog/{user_id}/list` под насыщающей конкурентностью
   (c=100, c=1000): throughput вырос на 6–18%, а p99-латентность на c=1000 сократилась
   более чем втрое (858.7ms → 269.6ms). Это ровно та ручка и та зона нагрузки, где в
   `before`-замере был зафиксирован потолок производительности Postgres.

2. **На низкой конкурентности (c=1, c=10) выигрыша от кэша нет** — поход в Redis Cluster
   добавляет сетевой round-trip, который не успевает окупиться, пока Postgres и так не
   загружен. Здесь `after` стабильно медленнее `before` на всех трёх ручках.

3. **`dialog_list` и запись в `dialog_send` просели на всех уровнях конкурентности**, хотя
   `dialog_list` кэш вообще не использует. Правдоподобное объяснение — дополнительная
   фоновая нагрузка от трёх нод Redis Cluster, работающих на том же 18-ядерном хосте
   одновременно с Postgres и приложением (в `before`-стенде Redis не было вовсе). Просадка
   `dialog_send` (который кэш таки трогает) меньше, чем у ничего не кэширующего
   `dialog_list`, — это говорит, что запись в Redis сама по себе не является доминирующим
   фактором деградации.

4. **Ошибок по-прежнему нет** ни на одном уровне нагрузки, вплоть до c=1000 — сервис
   остаётся стабильным, деградация выражается в росте латентности, а не в отказах.

5. **Для чистого измерения эффекта кэша** стоит повторить прогон, запустив Redis Cluster
   на отдельной машине (или хотя бы ограничив его CPU через `docker run --cpus`), чтобы
   исключить конкуренцию за ядра с Postgres и самим приложением на одном хосте.
